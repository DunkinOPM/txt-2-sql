# schema.md — Database Schema and Dataset Metadata

**Version:** 3.0  
**Status:** Updated baseline  
**Database:** PostgreSQL  
**Last updated:** 2026-10-24

## 1. Purpose

The application supports user-uploaded CSV/XLSX datasets and clarification-driven conversational Text-to-SQL. Uploaded data has a variable schema, so the database contains both stable application metadata tables and dynamically created tables for imported records.

This document defines:
1. Stable metadata tables for datasets, physical table mappings, and column metadata.
2. Dynamic-table naming and import conventions.
3. Query-history and clarification persistence recommendations.
4. Access control and SQL safety requirements.
5. The boundary between backend data contracts and frontend presentation.

## 2. Architecture Decisions

- PostgreSQL runs in Docker Compose during initial development and uses a named persistent volume.
- FastAPI runs locally during initial development and connects to PostgreSQL at `localhost:5432`.
- React + Vite + TypeScript is the frontend; Tailwind CSS styles project-owned native components, and Lucide React is the only icon pack.
- The UI consumes APIs and does not connect directly to PostgreSQL.
- Gemini is called by the backend, not by the browser.
- LangGraph orchestrates the query workflow inside the backend.
- Redis is not used in the initial version.
- CSV and XLSX are the only initial upload formats.
- Dataset ownership must be checked by backend code before schema disclosure, querying, or deletion.

## 3. Database Layout

Use a stable application schema (for example, `app`) for metadata and a controlled schema (for example, `uploaded_data`) for imported tables.

```text
PostgreSQL
├── app
│   ├── app_datasets
│   ├── app_dataset_tables
│   ├── app_dataset_columns
│   ├── app_queries
│   └── app_query_turns
└── uploaded_data
    ├── dataset_<backend_generated_id>
    ├── dataset_<backend_generated_id>
    └── ...
```

The names above are conventions. All dynamic identifiers must be generated and validated by backend code.

## 4. Stable Metadata Tables

The DDL below is a baseline. Add indexes, migrations, and ownership/authentication columns consistent with the chosen authentication model.

### 4.1 `app.app_datasets`

One row per uploaded dataset.

```sql
CREATE SCHEMA IF NOT EXISTS app;
CREATE SCHEMA IF NOT EXISTS uploaded_data;

CREATE TABLE app.app_datasets (
    id UUID PRIMARY KEY,
    owner_id TEXT NOT NULL,
    display_name TEXT NOT NULL,
    original_filename TEXT NOT NULL,
    file_format TEXT NOT NULL CHECK (file_format IN ('csv', 'xlsx')),
    status TEXT NOT NULL CHECK (
        status IN ('uploading', 'importing', 'ready', 'failed', 'deleting')
    ),
    row_count BIGINT NOT NULL DEFAULT 0 CHECK (row_count >= 0),
    column_count INTEGER NOT NULL DEFAULT 0 CHECK (column_count >= 0),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    error_code TEXT,
    error_message TEXT
);
```

Guidance:
- `id` is generated by the backend.
- `owner_id` refers to the authenticated user or the explicitly chosen initial session identity. The exact auth/session model remains a separate decision.
- Never use `original_filename` as a table identifier.
- Keep error messages user-safe; internal diagnostics belong in logs.
- Consider soft deletion only if product requirements need it.

### 4.2 `app.app_dataset_tables`

Maps a dataset ID to its backend-generated physical table.

```sql
CREATE TABLE app.app_dataset_tables (
    id UUID PRIMARY KEY,
    dataset_id UUID NOT NULL UNIQUE
        REFERENCES app.app_datasets(id) ON DELETE CASCADE,
    schema_name TEXT NOT NULL DEFAULT 'uploaded_data',
    table_name TEXT NOT NULL UNIQUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

The service must ensure the mapped schema/table is one it generated and controls. Do not accept a physical table name from a user or LLM as an authority.

### 4.3 `app.app_dataset_columns`

Stores display names and inferred types for schema discovery and UI display.

```sql
CREATE TABLE app.app_dataset_columns (
    id UUID PRIMARY KEY,
    dataset_id UUID NOT NULL
        REFERENCES app.app_datasets(id) ON DELETE CASCADE,
    ordinal_position INTEGER NOT NULL CHECK (ordinal_position > 0),
    original_name TEXT NOT NULL,
    internal_name TEXT NOT NULL,
    inferred_type TEXT NOT NULL,
    nullable BOOLEAN NOT NULL DEFAULT TRUE,
    sample_values JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (dataset_id, ordinal_position),
    UNIQUE (dataset_id, internal_name)
);
```

`sample_values` is optional and should contain only a small, safe sample. Do not store whole columns or sensitive values merely for prompting. If sample values are not needed, omit them or leave them null.

### 4.4 `app.app_queries`

Stores query requests and their final/current status. Whether full query history is retained should be configurable.

```sql
CREATE TABLE app.app_queries (
    id UUID PRIMARY KEY,
    dataset_id UUID NOT NULL
        REFERENCES app.app_datasets(id) ON DELETE CASCADE,
    owner_id TEXT NOT NULL,
    original_question TEXT NOT NULL,
    refined_question TEXT,
    category TEXT CHECK (category IN (
        'RELEVANT_CLEAR',
        'RELEVANT_AMBIGUOUS',
        'RELEVANT_UNANSWERABLE',
        'OUT_OF_SCOPE',
        'NONSENSICAL',
        'IMPROPER_OR_UNSAFE'
    )),
    status TEXT NOT NULL CHECK (status IN (
        'classifying',
        'awaiting_clarification',
        'generating_sql',
        'validating_sql',
        'executing',
        'completed',
        'rejected',
        'failed'
    )),
    generated_sql TEXT,
    explanation TEXT,
    result_row_count BIGINT,
    execution_duration_ms INTEGER,
    error_code TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

Do not store result payloads indefinitely by default. If results must be retained for history, apply row/size limits and an explicit retention policy. Always authorize access to a query through its owner and dataset.

### 4.5 `app.app_query_turns`

Stores clarification prompts and user responses for multi-turn workflows.

```sql
CREATE TABLE app.app_query_turns (
    id UUID PRIMARY KEY,
    query_id UUID NOT NULL
        REFERENCES app.app_queries(id) ON DELETE CASCADE,
    turn_number INTEGER NOT NULL CHECK (turn_number > 0),
    role TEXT NOT NULL CHECK (role IN ('assistant', 'user', 'system')),
    turn_type TEXT NOT NULL CHECK (
        turn_type IN ('question', 'clarification', 'clarification_answer', 'status', 'explanation')
    ),
    content TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (query_id, turn_number)
);
```

Do not expose internal system prompts or chain-of-thought. Persist only the user-visible conversational turns and the structured state required to resume the workflow.

## 5. Dynamic Imported Data Tables

Each successfully imported dataset receives a unique physical table, for example:

```text
uploaded_data.dataset_550e8400e29b41d4a716446655440000
```

The exact identifier format is an implementation detail; it must be generated by the backend, normalized to valid PostgreSQL identifier rules, and collision-checked.

### Naming and column rules

- Never derive SQL identifiers directly from a filename, user prompt, or LLM output.
- Preserve the original column label in `app_dataset_columns.original_name`.
- Create a safe, unique `internal_name` for SQL generation, such as `cgpa`, `student_name`, or `column_3`.
- Handle empty, duplicated, reserved-word, and punctuation-heavy headers deterministically.
- Quote identifiers safely using the database library when constructing DDL.
- Validate inferred types conservatively. Use text when type inference is uncertain.
- Preserve nulls consistently and avoid silently converting ambiguous values.
- Define explicit limits for row count, column count, file size, and cell size.

### Example college dataset

For an uploaded file with columns `Student Name`, `Department`, `CGPA`, and `Year`, metadata could map the display labels to internal names:

| Original header | Internal name | Inferred PostgreSQL type |
|---|---|---|
| Student Name | `student_name` | `TEXT` |
| Department | `department` | `TEXT` |
| CGPA | `cgpa` | `NUMERIC` |
| Year | `year` | `INTEGER` |

This is an example only. The actual imported schema must come from the uploaded file.

## 6. Import Transaction and Failure Handling

Recommended sequence:

1. Validate file and parse into a bounded in-memory or streaming representation.
2. Create metadata in an importing state.
3. Create the generated physical table.
4. Import records using SQLAlchemy/psycopg.
5. Write column metadata and row/column counts.
6. Mark the dataset `ready` and commit.
7. On failure, roll back when possible; otherwise drop any partially created table and mark the dataset failed with a safe error code/message.

Deletion should first authorize the owner, then remove the physical table and metadata in a controlled transaction/compensating cleanup flow. Avoid allowing arbitrary schema/table drops.

## 7. Query Execution and Access Control

### Required protections

- Resolve `dataset_id` from metadata and verify ownership before schema inspection, SQL generation, query execution, preview, or deletion.
- Build the allowed table list from backend metadata, never from model output.
- Execute generated SQL with a separate least-privilege read-only PostgreSQL role.
- Restrict access to the controlled uploaded-data schema and approved objects.
- Require one permitted read-only statement; reject mutations, DDL, administrative commands, transaction control, COPY, and multiple statements.
- Use SQLGlot plus explicit policy checks. Parsing alone is not sufficient.
- Apply statement timeouts and row limits.
- Revalidate any repaired SQL before re-execution.
- Avoid leaking internal table mappings for other datasets.
- Use backend parameter binding for values where possible; validate identifiers against registered metadata.

A read-only role should not own the uploaded tables and should not have schema-creation or table-modification privileges. Configure permissions carefully so the role can only read the intended dataset tables. If row-level isolation cannot be reliably enforced by database privileges alone, the backend must enforce a strict per-dataset table allowlist before execution.

## 8. Schema Context Sent to Gemini

Provide only the minimum context required for the task:
- Selected dataset's authorized columns and inferred types.
- Safe, relevant descriptions or a small sample of values when needed and permitted.
- The original question and user-provided clarification answers.
- Explicit SQL rules and expected structured response format.

Do not send the entire uploaded file by default. Do not include credentials, other users' datasets, or unrelated metadata. Treat model-generated SQL and classification as untrusted input requiring validation.

## 9. Frontend Data Contracts

The frontend does not read or modify database tables directly. It uses FastAPI endpoints and typed response models.

Recommended dataset summary fields:
- `id`
- `display_name`
- `file_format`
- `status`
- `row_count`
- `column_count`
- `created_at`

Recommended column fields:
- `original_name`
- `internal_name` (may be hidden from ordinary users if not useful)
- `inferred_type`
- `nullable`
- `ordinal_position`

Recommended query response fields:
- `query_id`
- `dataset_id`
- `status`
- `category`
- `assistant_message`
- `clarification_question` when awaiting clarification
- `generated_sql` when safe and available to display
- `columns` and bounded `rows` when completed
- `result_row_count`
- `execution_duration_ms` when available
- `error_code` and user-safe error message when failed

Exact API shapes should be defined as Pydantic models in the backend and mirrored by TypeScript types in the frontend. Do not treat client-side types or UI state as authorization controls.

## 10. Indexes and Constraints

At minimum, add indexes for common metadata access patterns:

```sql
CREATE INDEX idx_app_datasets_owner_created
    ON app.app_datasets (owner_id, created_at DESC);

CREATE INDEX idx_app_queries_owner_created
    ON app.app_queries (owner_id, created_at DESC);

CREATE INDEX idx_app_queries_dataset_created
    ON app.app_queries (dataset_id, created_at DESC);

CREATE INDEX idx_app_query_turns_query_turn
    ON app.app_query_turns (query_id, turn_number);
```

The `UNIQUE` constraint on `app_dataset_tables.dataset_id` ensures one registered physical table per dataset in the initial model. If a future feature supports multiple tables per uploaded dataset, revise this constraint and define relationships explicitly.

## 11. Migrations and Operational Notes

- Use a migration tool such as Alembic for stable application metadata tables.
- Dynamic uploaded tables are created and removed by the dataset service, not by manual migrations.
- Keep secrets in environment variables or a secret manager; never commit `.env`.
- Use Docker's named volume for local PostgreSQL persistence.
- Backups, retention, production authentication, audit requirements, and deployment-specific role configuration need to be defined before production release.
- Redis is not required for the initial version; persistent query/clarification state can be stored in PostgreSQL or a suitable LangGraph checkpointer.
